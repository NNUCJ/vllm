5 · 运行时：dense 三步、MoE 六步

对应报告 3.1–3.3 · 图 9、图 10、图 11
  • dense 三步里只有中间一步换后端，激活量化两条路共用同一批 csrc 算子——换 GEMM 不会让量化变快。
  • 图 10 讲清 [1,128] 与 [128,128] 的粒度耦合：片内 scale 为常数，反量化因子才能提出求和号。
  • MoE 六步 图 11，重点是 M_sum：Qwen3.6 prefill 256 token 时真实 2048 行、M_sum 却是 34560 行，≈17 倍膨胀只占显存不占算力（padding 行 expert_ids = −1 被跳过）。
  • 唯一的运行期重判定：TritonOrDeepGemmExperts 每次 forward 二选一。
dense 构造期定死，MoE 只有 Fallback 系列会逐次重判。

6 · 原理：UE8M0 与 fp32 是两条反量化通路

对应报告 4.1–4.3 · 图 12、图 13 · 表 18
  • 数学起点：乘 2 的幂只改指数域、不动尾数，不需要乘法器且逐位精确。
  • DeepGEMM 走硬件通路——scale 作为 E8M0 字节进 tcgen05 block-scaled MMA；CUTLASS 走软件通路——ElementBlockScale = float，在 CUDA core 上做 promotion 图 12。
  • 代价：scale 上取整到 2ⁿ，block amax 只能映射到 256 而非 448，上端最多让出 1 bit 动态范围。附录 B 实测量化误差放大 ×1.37。
  • 一句话对比 表 18：DeepGEMM 的能力边界在运行期（JIT），CUTLASS 的在编译期（AOT）。
这 1 bit 就是下一段黑名单的全部根因。

讲者备忘：大概率会被问到

改 VLLM_USE_DEEP_GEMM_E8M0=0 不就没精度问题了？
能消除根源，但黑名单按 model_type 一刀切、不看 scale 格式，依然命中。
那把 quant_config.use_deep_gemm 改回 True 呢？
没用。判定写在两处，真正让候选落选的是 can_implement 里的独立调用；改配置只会让反量化守卫失效 表 25。
是不是 N/K 没对齐才选不上 DeepGEMM？
block-FP8 基本不可能。建层时的 validate_fp8_block_shape 要求 128 对齐，比 DeepGEMM 的 64/128 更严，不满足会直接 raise。
MoE 选中 DEEPGEMM 就一定跑 DeepGEMM 吗？
不一定。_valid_deep_gemm 有 N <= 512 一条，对这份权重恰好命中；默认 E8M0 开启会把它短路，关掉则每次 forward 回退 Triton。
这套结论对别的 FP8 模型也成立吗？
机制成立，结论不成立。黑名单只有两个 model_type；换模型请用 表 28 的推演方式自己走一遍。
